# p002 design: an LLM planner against the clause router

Pre-registered 2026-09-25, before either model was scored on these requests.

## Question
r001's router labels one clause at a time, and code splits the clauses. It cannot express "twice",
"for three seconds", or "and" joining two actions, and it wrongly splits "X, looking down". A
small open LLM, **Gemma 4 E4B** (google/gemma-4-E4B-it-qat-q4_0-gguf, llama.cpp on CPU), writes
the whole plan, and its output is grammar-constrained to the router's own labels
(`src/duckbatch/planner.py`). Does it plan multi-step requests better?

## Set
30 requests (`menus/p002-plan-requests.yaml`) in six groups: repetition, durations, "and"-joined,
single steps with modifiers, longer sequences and colloquial requests, plus 5 out of scope (3
whole, 2 partial). The four smoke-test requests are not in the set.

## Scoring (code: `planner.evaluate`)
- **sequence exact**: the unrolled action sequence equals gold (consecutive `unsupported` collapsed).
- **fully exact**: sequence exact, and every scored label (speed, head, sound) and stated
  duration is right.
- per-head label accuracy on requests whose sequence matched.
- refusal: whole out-of-scope requests planned as only `unsupported`.
- latency per request (CPU, 16 threads, the laptop).
The router baseline is Decide (r001's better model); it has no repeat or duration, so repeat=1.

## Predictions / pass lines
1. Gemma's sequence exact ≥ router's + 20 points (the gain the planner exists for).
2. Gemma refuses ≥ 2 of the 3 whole out-of-scope requests.
3. Recorded, not a pass line: latency. The smoke test ran at 30–50 s per plan on CPU, far too
   slow for a phone round trip, so this is the number that decides between E2B, GPU offload, or
   an on-device Apple model.
